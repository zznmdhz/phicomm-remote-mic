# Kehwin 私有语音协议（斐讯 N1 / DB1-R 蓝牙语音遥控器）

本文档描述斐讯 N1/DB1-R 蓝牙语音遥控器的 BLE 语音通道协议。所有命令与帧格式均于 **2026-10-29 在真机上端到端验证**（环回重建相关度 0.998、真人语音 ASR 可辨），协议内容来自对官方驱动包内厂商参考实现的静态逆向分析，研究过程见 [RESEARCH.md](RESEARCH.md)。

## 1. 设备信息

| 项目 | 值 |
| --- | --- |
| 设备名 | 斐讯遥控器 |
| 型号 | DB1-R / BD1-R（N1 语音遥控器） |
| 芯片 | Realtek RTL8762AK |
| HID VID:PID | `005D:0001` |
| BLE DIS Model | 0.9 |
| BLE DIS 软件版本 | `RTL_618_V0001` / `100011_201908241450` |
| MAC 样例 | `00:E0:4C:2C:04:B6` |
| 配对组合键 | **主页 + 音量-** |

HID 层只有两个 top-level collection：键盘（report 1）与 consumer controls（report 2），描述符中**没有** HID audio 报告——语音不走 HID 音频，走下述自定义 GATT 服务。

## 2. GATT 服务表

| 服务 | 类型 | 说明 |
| --- | --- | --- |
| `0x1800` | GAP | 标准 |
| `0x1801` | GATT | 标准 |
| `0x180A` | Device Information | 标准（含上表 DIS 字段） |
| `0x180F` | Battery | 标准 |
| `0x1812` | HID | 标准；被 OS 保护，bleak 枚举时会被省略，但 PnP/HID 证据可证明其存在 |
| `d0ff` / `6287` | 公模服务，base UUID `3C17-D293-8E48-14FE-2E4DA212` | 疑似 Realtek OTA/DFU。**禁止写入**任何数据 |
| `0x1920` | 自定义 | **语音通道**（详见下节） |

## 3. 语音通道（服务 0x1920）

| 特征 | 权限 | 方向 | 说明 |
| --- | --- | --- | --- |
| `2B00` | notify / read | 下行 | 音频 + 控制数据，遥控器 → 主机 |
| `2B01` | write / read / write-no-response | 上行 | 20 字节命令，主机 → 遥控器 |

- CCCD 默认值 `0100`（notify 已使能）；两个特征 read 均返回 20 字节零。
- 命令统一写 `2B01`，**使用 write with response**。

## 4. 握手与开流

**关键事实：语音键按下时 GATT 零自发流量**——遥控器不会主动推音频，必须主机先握手并开流（这也是最初被动订阅方案失败的原因）。全部命令为 20 字节：

| 步骤 | 命令（hex） | 时机 | 说明 |
| --- | --- | --- | --- |
| 1. 挑战应答 | `08 01` + rand32 + `01 03` + `12×00` | 连接后立即 | rand32 为 31-bit 随机数，little-endian，占 4 字节；`01 03` 为固定子命令 |
| 2. 应答确认 | `08 0C` + `4×00` + `01` + `13×00` | 步骤 1 之后 **300 ms** | 固定命令，间隔不可省略 |
| 3. 开流 | `08 06 01` + `17×00` | 应答确认之后 | 开始推送音频 |
| 停止 | `08 06 00` + `17×00` | 任意时刻（必须发） | 停止推流；**关闭/异常退出前必须发送** |

命令长度核对：`08 01`（2）+ rand32（4）+ `01 03`（2）+ 12 零 = 20 字节；`08 0C`（2）+ 4 零 + `01`（1）+ 13 零 = 20 字节；`08 06 01/00`（3）+ 17 零 = 20 字节。

## 5. 音频帧格式

### 5.1 常规 120 字节通知包

`2B00` 的常规通知包固定 120 字节，内含 **2 × 60 字节 H2 mSBC 帧**：

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 1 | H2 头，固定 `0x01` |
| 1 | 1 | （帧内字段） |
| 2 | 1 | mSBC syncword `0xAD` |
| 2..58 | 57 | mSBC 帧体（`bytes[2:59]`，喂给解码器的有效载荷） |
| 59 | 1 | （帧尾） |
| 60..119 | 60 | 第二帧，结构同上 |

- 编码：mSBC（MSBC），**16 kHz、单声道**，7.5 ms/帧，即 120 字节包 ≈ 15 ms 音频。
- 解码：取出每帧的 57 字节后用 `ffmpeg -f sbc` 解码为 `pcm_s16le`。

### 5.2 20 字节分片包

部分通知包只有 20 字节，是 120 字节包的分片：

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 1 | 低 5 位 == `20`，标识这是分片包 |
| 1 | 1 | 序号 `1..7` |
| 2.. | 18 | 分片数据 |

按序号重组（1..7 连续收齐）即可还原为 120 字节包，再按 5.1 解析。重组逻辑见 `app/remote_mic.py`。

## 6. 工程注意事项

1. **bleak 直构对象绕过扫描**：已配对/已连接的设备可能不再广播，用字符串地址扫描会失败。用 `BLEDevice(address, '名', None)` 直接构造对象即可秒连。
2. **WinRT 需 `use_cached_services=False`**：否则可能拿到过期的服务表。
3. **音频工作线程必须先 `CoInitializeEx(MTA)` 再启动 WASAPI 流**：否则后台线程 `stream.start()` 会报令人费解的 stale WDM-KS 错误；MTA 初始化后同一 worker 里的 bleak 也可正常工作。
4. **停止必须发 `08 06 00 …`**：否则遥控器保持开流状态。
5. **禁止写 d0ff / 6287**：疑似 OTA/DFU 服务，误写有变砖风险。
6. **不要照搬 Realtek 新 SDK 文档**：其参考设计用自定义 vendor service `000003FD`（特征 `3A40`/`3A41`），与本遥控器的 `0x1920` 通道不一致，命令/编解码不能互相假定。

## 8. 协议来源

- 逆向方法：**Codex CLI** 对官方驱动包内 `KehwinBLE.apk` 用 JADX 1.5.6 做静态反编译，对 `lib/arm/libmbleRuntime.so` 用 capstone / pyelftools 分析；**未执行**任何第三方 APK 或 native 库。
- 驱动包来源：恩山论坛固件作者原帖 <https://www.right.com.cn/forum/thread-4078508-1-1.html>（百度网盘分享，提取码 `jasu`，`DB1-R_VOICE.7z`，14,316,816 字节）。
- 交叉验证：Hermes Agent 真机 GATT 实验台对服务表、特征权限、握手时序与音频流做了独立复核。
